# 08 · 历史决策（ADR 式记录）

> 记录「**为什么**这么做」而不是「做了什么」。
> 接手的人最容易犯的错，就是把一个看起来多余的约束「优化」掉，然后重新踩一遍坑。

---

## ADR-001：为什么用 go_router 而不是裸 Navigator

**决策**：路由全部用 `context.go()` / `context.push()`，禁用 `Navigator.pushNamed`。

**原因**：官方维护、支持深链、可声明式做守卫、路由集中一处可审计。

**代价与坑**：go_router 接管了根 Navigator，裸 `pushNamed` 在真机上**静默失败**
（表现为「点了没反应」，日志里什么都没有）。v1.3.0 踩过这个坑。

**现状**：`lib/app/router.dart` 里 7 条路由全部声明式定义，文件头有明确警告注释。

## ADR-002：为什么 router.dart 里有 `FestivalSelectionHost` 包装器

**决策**：加一个薄包装 Widget，直接 `ref.watch(selectionProvider)` 取状态。

**原因**：早期版本靠层层传参把状态往下传，结果节日选择页和时间轴看到的
勾选状态不同步。包装器读 Riverpod 状态，问题消失。

**代价**：多一层 Widget。可接受。

## ADR-003：为什么 `/settings` 曾指向错页面

**决策（修正后）**：`/settings` 指向 `SettingsPage`（真设置页），
`/festival-selection` 才是节日选择模板页。

**原因**：v1.3.0 的 bug —— `/settings` 错误指向 `FestivalSelectionHost`，
导致点「设置」进的是模板页。

**现状**：代码里有注释标记，防止改回去。

## ADR-004：为什么 domain 层禁止 import flutter

**决策**：`domain/` 只用 `dart:core`，不 import `package:flutter/*`，
也不 import `data/`。

**原因**：
1. 业务规则（农历换算、循环判定、日期解析）能脱离 UI 单测
2. 换存储或换框架时不用重写业务逻辑
3. 强制 UI 和业务解耦，避免把 `BuildContext` 漏进领域模型

**验证**：`test/lunar_engine_test.dart` 直接裸测 `LunarEngine`，
不需要 `testWidgets`，不需要渲染任何东西。

**代价**：领域模型不能用 Flutter 的值类型（如 `Color`）。

## ADR-005：为什么记录以「节日 + 年份」为粒度

**决策**：`MemoryRecord` 的语义是「**`[festivalId]` 在 `[year]` 年发生的那一次**」。
id 里带年份，索引是 `(festival_id, year)`。

**原因**：2026 中秋和 2027 中秋是**两次不同的经历**，不是同一条记录的两次编辑。
用户去年中秋写的内容，今年不该被覆盖。

**验证**：`test/ui_smoke_test.dart` 的 T2 用例专门测这个 ——
「同节日跨年份是两条独立记录」。

## ADR-006：为什么 `asFestival()` 故意丢掉年份信息

**决策**：`CustomFestival.asFestival()` 返回的 `Festival` **不携带 `anchorYear`**。

**原因**：这个方法的用途是「把它当成一个普通 Festival，用于列表分类、图标、
提示词模板」。这些场景不需要也不应该关心年份。把 `anchorYear` 塞进去会让
`asFestival()` 变成一个「看起来什么都能干」的方法，然后有人拿它去算日期，
「仅此一次」就又变成每年都出现了。

**配套铁律**：**真实日期一律走 `CustomFestival.dateIn(year)`**，
全项目统一用 `resolveDateIn()` helper。

**代价**：容易踩坑。缓解手段是文件头注释 + `AGENTS.md` 陷阱清单 + 本 ADR。

## ADR-007：为什么要引入 `resolveDateIn()` 统一 helper

**决策**：所有需要算节日真实日期的地方，都调
`record_providers.dart` 里的 `resolveDateIn(id, year, customs, resolved)`。

**原因**：ADR-006 的代价。散落在各处的 `festival.dateIn(year)` 调用，
总会有人漏掉 `anchorYear` 约束。集中到一个函数，只有一处需要正确。

**签名设计**：故意把 `customs` 和 `resolved` 都作为参数传入而不是内部去读 provider，
让它是个纯函数 —— 测试里可以直接调用，不必搭 ProviderScope。

## ADR-008：为什么 `main()` 要注入启动快照

**决策**：`customFestivalsSnapshotProvider` 在 `main()` 里
`overrideWithValue(customs)`。

**原因**（两个）：
1. **性能**：首帧不用再查一次 SQLite
2. **一致性**：resolver 和 timeline 看到的是同一份数据。
   否则可能出现「时间轴列出了某节日，但日期算不出来」的不一致

**代价**：新增/删除自定义节日后必须**回写快照**，否则新数据会被旧快照冻住。
已在 `CustomFestivalActions.save/delete` 里处理，并在文件头注释标明。

**测试环境兼容**：默认值是 `null`，表示「未注入」，此时 provider 走实时查询。

## ADR-009：为什么 `registerKnownIds()` 是静态方法

**决策**：`SuiyaStorage.extraKnownIds` 是**静态** Set，通过静态方法 `registerKnownIds()` 注入。

**原因**：调用点在 `main()`，那时 Riverpod 还没起来，没有 provider 可用。
而 `_festivalExists()` 是 `SuiyaStorage` 的静态私有方法，不走实例。

**代价**：全局可变状态。但因为是**单次调用（在 runApp 之前）**，实际风险很低。
`registerKnownIds()` 内部会 `clear()` 再 `addAll()`，所以重复调用是幂等的。

**现状**：注释里明确写了「应在 runApp 之前调用」。

## ADR-010：为什么数据库 SQL 集中在 `schema.dart`

**决策**：所有建表和迁移 SQL 集中在 `lib/core/db/schema.dart`，
业务代码里禁止写裸 SQL。

**原因**：
1. 迁移链是**顺序敏感**的，散落各处必然出错
2. 新增列时需要 `PRAGMA table_info` 幂等检查、可能还要回填历史数据 ——
   这套逻辑需要一个明确的地方
3. 便于审计：改一个文件就知道数据库全貌

**收益**：v1 漏建 `places.festival_tags` 列导致**保存地点必抛异常**，
就是散落 SQL 的典型后果。v2 补上了，并加了注释标记。

## ADR-011：为什么迁移分支不能改

**决策**：v1→v2→v3 的迁移代码**只能往前加，不能修改或删除已有分支**。

**原因**：这些迁移**都已在真机上跑过**。
用户的设备上数据库已经从 v1 升到 v2，现在要升到 v3。
如果改了 v2→v3 的逻辑，那些已经跑过 v2 的设备会遇到不匹配的中间状态。

**规矩**：`migrate()` 里新增 `if (from < 4 && to >= 4)` 这样的分支，
永远不动上面已有的。

## ADR-012：为什么图片不入库

**决策**：图片存文件系统，数据库只存路径（`media` 表的 `path` 列）。

**原因**：SQLite 存 BLOB 会让数据库文件暴涨，查询变慢，备份也难处理。
`MediaStore` 负责压缩、命名、清理孤儿文件。

**备份时的处理**：`BackupService` 导出时把所有图片打包成 zip 再 base64 塞进 JSON，
导入时解出来还原。见 `03-数据层.md`。

## ADR-013：为什么加密备份用 PBKDF2 + AES-GCM

**决策**：PBKDF2 从密码派生密钥 → `AesGcm.with256bits()` 加密，带 MAC 校验。

**原因**：
- **GCM 提供完整性校验**：密文被改过会检出，不会静默解出垃圾数据
- **PBKDF2 迭代** 拖慢暴力破解
- 无服务端，密码丢了**真的解不开**，这是隐私优先的代价，符合产品定位

**提示用户**：导出时要说清楚密码丢失 = 数据永久丢失。

## ADR-014：为什么不联网 / 不做多设备同步

**决策**：应用**零网络能力**，不引入账号体系，所有数据本地存储。

**原因**：这是产品底线，不是技术限制。用户的记录内容（墓园、纪念、
家庭隐私）不应该离开设备。

**落地方式**：
- `SyncPolicy.localOnly` 是默认值
- `url_launcher` 只用于**调起外部地图 App**，不用于打开 URL
- 新增依赖前必须确认它不隐式发起网络请求

**遗留冲突**：「多设备同步」在 `05-待办与路线图.md` 里被标为 P2，
但实现它**与本 ADR 冲突**，需要产品层面决策（可能只能做「用户手动导出/导入」）。

## ADR-015：为什么图片保存在 C 盘之外有风险 —— 工具链布局

**决策**：工程和 Flutter SDK 放 D 盘，JDK / Android SDK 在
`C:\Users\XX\.workbuddy\binaries\`。

**原因**：用户明确要求「工程和 SDK 尽量放 D 盘」。
JDK 和 Android SDK 是工具链统一存放处（WorkBuddy 管理），不动。

**注意**：`android/local.properties` 写死了绝对路径，**换机器必须重写**。
这也是为什么它不该被提交。

## ADR-016：为什么注释要写「为什么」

**决策**：代码注释用中文，重点解释**为什么这样写**、有什么坑，
而不是复述代码在做什么。

**原因**：项目里有大量这样的注释，比如：

```dart
/// 自定义节日存在 SQLite 里，但 SharedPreferences 只存 id 字符串。
/// 必须在读取「勾选了哪些日子」之前把 custom id 注册进 SuiyaStorage，
/// 否则冷启动会把它们当成已不存在的节日过滤掉（v1.4.0 的真实 bug）。
```

这段注释的价值在于：**半年后有人想「优化」掉这个注册调用时，
会立刻意识到这是个坑**。复述代码的注释则毫无价值。

**约定**：接手后继续沿用这个风格，不要改成只写代码在做什么。

## ADR-017：为什么每次打包前必须升版本号

**决策**：每次打包交付前，先升级版本号，三处同步改。

**原因**：用户明确要求。工程没有自动化版本管理，靠人工纪律。
如果忘了升，用户装的还是旧版，会以为「修复没生效」。

**三处**：`pubspec.yaml` / `android/local.properties` / `settings_page.dart` 关于页。
缺一处，真机上显示的版本就会错。

**验证**：交付前用 `aapt dump badging` 验产物，不信 pubspec。
