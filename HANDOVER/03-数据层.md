## 版本历史（不可重写）

| 版本 | 内容 |
|---|---|
| **v1** | `records` / `media` / `places` / `tags` / `reminders` |
| **v2** | ① `places` 补 `festival_tags` 列（v1 漏建，**导致保存地点必抛异常**）<br>② 新增 `custom_festivals`（用户自定义日子）<br>③ 新增 `presets`（同行的人 / 标签预设）<br>④ 新增 `logs`（info / warning / error 三级） |
| **v3** | `custom_festivals` 补 `anchor_year` 列 —— 修复「仅此一次」实际每年都出现的语义 bug |

v1→v2→v3 的迁移**都已在真机跑过**。
`migrate()` 里**只能往前加分支，不能修改或删除已有分支**。

> **v3 之后无 schema 变更**（数据库版本仍为 3）：
> WebDAV 云备份（v1.5.0）的配置走 SharedPreferences、密码走 secure storage；
> 地点照片（v1.5.1）复用 `media` 表。两者都没有新增表或列。

## 表结构

### `records` —— 记录主体

```sql
CREATE TABLE records (
  id            TEXT PRIMARY KEY,
  festival_id   TEXT,                          -- 关联节日 id，可空 = 纯自定义记录
  year          INTEGER NOT NULL,
  title         TEXT NOT NULL,
  text          TEXT DEFAULT '',
  qa_json       TEXT DEFAULT '[]',             -- 结构化问答
  recurrence    TEXT NOT NULL DEFAULT 'once',
  advance_days  INTEGER DEFAULT 1,             -- 提前几天提醒
  remind_on     INTEGER DEFAULT 0,
  participants  TEXT DEFAULT '[]',
  tags          TEXT DEFAULT '[]',
  lat REAL, lng REAL,                          -- 手动选的坐标
  place_id      TEXT,                          -- 关联 places
  address       TEXT,
  sync_policy   TEXT DEFAULT 'LOCAL_ONLY',     -- 隐私红线，默认绝不上传
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE INDEX idx_rec_year  ON records(year);
CREATE INDEX idx_rec_fest  ON records(festival_id, year);
```

**核心语义**：`[festivalId] 在 [year] 年发生的那一次`。
所以**同一个节日在不同年份是不同记录**（2026 中秋 ≠ 2027 中秋），
id 里带年份，schema 索引也是 `(festival_id, year)`。

### `media` —— 图片

```sql
CREATE TABLE media (
  id          TEXT PRIMARY KEY,
  record_id   TEXT NOT NULL,     -- 记录 id 或地点 id（v1.5.1 起地点照片复用本表）
  kind        TEXT NOT NULL,     -- 'photo'
  path        TEXT NOT NULL,     -- 本地文件绝对路径
  bytes       INTEGER,
  ...
);
CREATE INDEX idx_media_rec ON media(record_id);
```

图片**不入库**，存文件系统，数据库只存路径。
`MediaStore` 负责压缩、命名、清理孤儿文件。

**复用约定**：`record_id` 既存记录 id，也存地点 id（v1.5.1 地点照片）——
查询侧用 `mediaOfProvider(记录id)` / `placePhotosProvider(地点id)` 两个 family 区分。
地点照片与记录照片共用同一套压缩、存储、孤儿清理逻辑，**无独立表、无新迁移**。

## 迁移写法（模板）

新增列的标准流程，**照抄这个模式**：

```dart
if (from < 4 && to >= 4) {
  // 先检查列是否已存在 —— 幂等，避免重复迁移报错
  final cols = await db.rawQuery('PRAGMA table_info($tRecords)');
  final names = cols.map((c) => c['name'] as String).toSet();
  if (!names.contains('new_column')) {
    await db.execute('ALTER TABLE $tRecords ADD COLUMN new_column TEXT');
    // 历史数据回填
    await db.execute("UPDATE $tRecords SET new_column = ... WHERE new_column IS NULL");
  }
}
```

同时要更新文件头的版本历史注释。

## SharedPreferences（`core/storage.dart`）

不是所有状态都该进库。轻量偏好走 `SuiyaStorage`：

- 用户勾选了哪些节日（**只存 id 字符串**）
- 日志等级
- 主题相关
- 首次启动标记

### 关键机制：`extraKnownIds`

SharedPreferences 存的只是节日 id，读回来时要用 `_festivalExists()` 过滤脏数据。
但 v1.4.0 之前它只认内置节日和二十四节气，**不认识 `custom_*` id**，
导致自定义节日的勾选状态在冷启动后被当脏数据丢掉
（表现为「重启后自定义节日消失 / 变成未勾选」）。

```dart
/// 额外认可的节日 id —— 目前只有用户自定义节日（custom_ 前缀）
static final Set<String> extraKnownIds = <String>{};

/// 注入自定义节日 id（必须在 runApp 之前、读 SharedPreferences 之前调用）
static void registerKnownIds(Iterable<String> ids) {
  extraKnownIds..clear()..addAll(ids);
}

static bool _festivalExists(String id) {
  if (extraKnownIds.contains(id)) return true;      // ← 优先检查
  if (Festivals.byId(id) != null) return true;
  return Festivals.allTerms().any((e) => e.id == id);
}
```

**新增任何自定义 id 体系时，都要在这里注册，否则冷启动丢数据。**

## 备份格式（`features/backup/service/backup_service.dart`）

两种导出：

### 1. 明文 JSON

```dart
Future<String> exportPlainJson()   // 人类可读，适合自己看/迁移
```

### 2. 加密归档（推荐）

```dart
Future<ExportResult> exportEncrypted(String password)
```

结构：

```
{
  "format": "suiya.archive",
  "version": <n>,
  "exportedAt": <ts>,
  "data": { ...全部表 dump... },
  "mediaZip": "<base64 的 zip>",     // 图片打包成 zip 再 base64
  "salt": "<base64>",
  "nonce": "<base64>",
  "mac":   "<base64>"
}
```

加密：`PBKDF2(密码, salt, 迭代)` 派生密钥 → `AesGcm.with256bits()`。
有 MAC 校验，改了密文会被检出。**密码丢了就真的解不开了**，没有后门。

导入提供三种模式（`ImportMode`）：合并 / 覆盖 / 仅恢复媒体。

> **注意**：备份里包含墓园、纪念记录等敏感内容。
> 分享导出文件前提醒用户确认，走明文 JSON 尤其要小心。

## WebDAV 云备份（v1.5.0，`features/webdav/`）

把上面两种备份文件上传到**用户自己的** WebDAV 网盘。**隐私边界**：
- Manifest 的 `INTERNET` 权限就是为它加的（v1.5.0 前刻意不联网）
- 仅在用户主动点「测试连接 / 备份 / 恢复」时联网；无后台任务、无遥测
- 数据直连用户的网盘，不经过任何岁忆自有服务器

结构（四层，同其他 feature）：

```
lib/features/webdav/
├── domain/webdav_config.dart            # 预设枚举/配置模型/buildFileName/URL 规整（纯 Dart）
├── data/webdav_client.dart              # dart:io 手写 PROPFIND/MKCOL/PUT/GET/DELETE + Basic Auth
├── data/webdav_store.dart               # 配置存 SharedPreferences；密码存 flutter_secure_storage（Keystore）
├── service/webdav_backup_service.dart   # 上传（加密/明文双模式）/列版本/恢复 + 多版本清理
└── presentation/webdav_page.dart        # /webdav 页（设置页入口）
```

要点：
- **不引第三方 WebDAV 库**（避免 http 依赖链）；XML 解析用 `xml` 包，按 local name 匹配（厂商前缀 d:/D: 不统一）
- **加密可选**（用户要求）：加密 = `.suiya` 含照片需口令；明文 = `.json` 不含照片，UI 警示后可用
- **时间戳多版本**：文件名模板 `{date}-backup.suiya`，每次上传独立文件；
  上传后 PROPFIND 按时间排序 DELETE 超量旧版本（best-effort，默认保留 5 份，1-20 可配）
- 配置存 `suiya.webdav.v1`（SharedPreferences JSON）；密码存 secure storage key `suiya.webdav.pass`
- 恢复走临时文件 + 后缀分流，provider 刷新集合与 `_doImport` 一致（records/places/timeline/yearReview + refreshFromDb）

> 与 Gradle 8.14.3 wrapper 可重新评估是否移除。
